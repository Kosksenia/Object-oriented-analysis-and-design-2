# Лабораторная работа №4

## Архитектурный паттерн «Коллекция объектов» (Unit of Work + Repository): Pokémon Manager — полноценная RPG-игра

### Предметная область

Паттерн **«Коллекция объектов» (Unit of Work)** широко применяется в разработке приложений, где требуется работать с базами данных и обеспечивать целостность данных при выполнении сложных бизнес-операций. Один из примеров — полноценная RPG-игра с коллекционированием, битвами и обменом.

**Pokémon Manager** — это полноценная RPG-игра с графическим интерфейсом, где игрок может:

- Выбрать стартового покемона
- Путешествовать по разным локациям
- Ловить диких покемонов
- Эволюционировать покемонов с анимацией
- Сражаться в пошаговых битвах
- Участвовать в турнирах
- Обмениваться покемонами с другими тренерами
- Отслеживать достижения в Покедексе
- Покупать предметы в магазине

### Описание проблемы

В процессе игры одно действие игрока затрагивает несколько таблиц базы данных. Например:

- Поимка покемона требует добавления записи о покемоне, списания покебола из инвентаря и обновления счётчика покемонов у тренера
- Эволюция требует изменения имени покемона, улучшения его характеристик и добавления достижения
- Обмен требует создания записи об обмене, передачи покемона другому тренеру и обновления счётчиков покемонов у двух тренеров
- Битва требует обновления опыта покемона, денег тренера и сохранения результата битвы

Если клиентский код будет напрямую выполнять каждую операцию отдельно, возникают серьёзные проблемы.

**Первая проблема — потеря согласованности данных.** При сбое на любом этапе данные становятся несогласованными. Покебол может быть списан, а покемон не добавлен. Покемон может эволюционировать, а опыт не начислен. При обмене покемон может исчезнуть у одного тренера, но не появиться у другого.

**Вторая проблема — невозможность отката.** Частично выполненные операции невозможно отменить без дополнительного кода.

**Третья проблема — сложность поддержки транзакций.** Ручное управление BEGIN TRANSACTION и ROLLBACK в каждом действии приводит к дублированию кода.

**Четвёртая проблема — нарушение принципа единственной ответственности.** Бизнес-логика смешивается с логикой управления транзакциями.

### Решение проблемы

Решение заключается в использовании паттерна «Коллекция объектов» (Unit of Work) в связке с Repository для координации всех операций с базой данных.

Паттерн гарантирует следующие преимущества.

**Единая транзакция.** Все изменения регистрируются в Unit of Work и фиксируются только при успешном завершении всех операций.

**Автоматический откат.** При любой ошибке выполняется rollback, данные остаются целыми.

**Разделение ответственности.** Repository отвечает за доступ к данным, Unit of Work — за координацию транзакций, Service — за бизнес-логику.

**Атомарность операций.** Либо все изменения сохранены, либо ни одно.

**Простота расширения.** Добавление нового действия не требует изменения логики транзакций — достаточно зарегистрировать новые операции в Unit of Work.

### Ключевые особенности реализации

#### Поимка покемонов

В версии с паттерном пользователь может ловить диких покемонов через графический интерфейс. Сначала игрок нажимает кнопку поимки, затем появляется дикий покемон, выбранный случайным образом из доступных. После подтверждения поимки все операции — добавление покемона, обновление счётчика тренера и списание покебола — регистрируются в Unit of Work и выполняются атомарно.

В версии без паттерна каждая операция выполняется отдельно, поэтому при сбое данные повреждаются.

#### Эволюция покемонов с анимацией

Версия с паттерном поддерживает полноценную эволюцию. Игрок нажимает кнопку эволюции, выбирает покемона, готового к эволюции (достигнут нужный уровень), после чего запускается анимация эволюции с прогресс-баром. Обновление имени, характеристик и достижений выполняется в одной транзакции.

В версии без паттерна возможна частичная эволюция, когда имя изменено, а характеристики нет.

#### Безопасный обмен покемонами

Обмен затрагивает пять таблиц — это самый сложный сценарий. Игрок нажимает кнопку обмена, выбирает покемона и указывает ID тренера-получателя. С паттерном регистрируются все пять операций, после чего выполняется commit, и данные остаются согласованными. Без паттерна при сбое покемон исчезает у одного тренера и не появляется у другого.

#### Битвы и сохранение результатов

Игрок нажимает кнопку битвы, запускается анимация с визуальными эффектами. С паттерном результат битвы сохраняется атомарно — опыт, деньги и запись о битве фиксируются одновременно. Без паттерна при сбое опыт может быть начислен без записи о битве или наоборот.

#### Визуальная индикация режима работы

Версия с паттерном имеет синий и зелёный интерфейс. Версия без паттерна имеет красный интерфейс с предупреждением об опасности.

### Преимущества реализации с паттерном

Реализация с паттерном Unit of Work обеспечивает транзакционность и автоматический rollback, тогда как без паттерна эти возможности отсутствуют.

При поимке покемона версия без паттерна несёт риск потери покебола, а версия с паттерном гарантирует, что либо всё сохранится, либо ничего.

При эволюции версия без паттерна может выполнить изменение только части данных, а версия с паттерном обеспечивает полное и атомарное обновление.

При обмене, затрагивающем пять таблиц, версия без паттерна гарантированно приводит к повреждению данных при сбое, тогда как версия с паттерном делает обмен полностью безопасным.

При битве версия без паттерна может потерять результаты, а версия с паттерном надёжно сохраняет их.

В магазине версия без паттерна может списать деньги без выдачи товара, а версия с паттерном обеспечивает транзакционную покупку.

Расширяемость в версии без паттерна сложная, требует изменения существующего кода, а в версии с паттерном простая — достаточно добавить новые операции в Unit of Work.

### Анимации и визуальные эффекты

В версии с паттерном реализованы следующие анимации.

Анимация поимки показывает, как покебол трясётся, сопровождается вспышками и сообщением об успехе.

Анимация эволюции представляет собой последовательную смену кадров с прогресс-баром.

Анимация битвы включает VS-экран и сообщения об атаках.

Также предусмотрены эмодзи для покемонов, которые используются при отсутствии загруженных картинок.

### Вывод

Паттерн «Коллекция объектов» (Unit of Work) в связке с Repository позволил создать надёжную, безопасную и расширяемую RPG-игру, в которой все действия с базой данных выполняются атомарно. Это наглядно демонстрирует преимущества паттерна.

Во-первых, обеспечивается целостность данных — либо все изменения сохранены, либо ни одно.

Во-вторых, реализован автоматический откат — при ошибке данные возвращаются в исходное состояние.

В-третьих, достигнуто разделение ответственности: Repository отвечает за доступ к данным, Unit of Work — за транзакции, Service — за бизнес-логику.

В-четвёртых, упрощён клиентский код — сервис просто регистрирует операции и вызывает commit.

В-пятых, обеспечена расширяемость — новые действия легко добавляются без изменения логики транзакций.

Версия без паттерна, напротив, показывает все проблемы отсутствия транзакционной координации: потерянные покебалы, частично эволюционировавшие покемоны, исчезнувшие при обмене покемоны и несохранённые результаты битв.
